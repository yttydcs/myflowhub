### P07 — 节点可组合多个功能，Flow 可独立也可集成

确认 Flow 可以独立运行，也可以集成到普通节点；一个节点可以实现一部分或者所有功能，不受“一节点一功能”约束。独立运行是可选形态，不得将每项功能强制拆成独立 Node、身份、进程或安装包。P04 的 hub/flow 是功能职责划分，不推导为固定节点种类。集成形态不能继续套用上一轮建议中 Flow 必须拥有独立节点身份的含义。

### P08 — Flow 使用节点权限，不单独限权

问题：同一节点内不同 Flow 是否需要分别限制可访问资源和可执行操作；助手曾建议在节点网络权限上限内进一步收窄。

用户原文：

> 不需要单独限制，flow实际上就是指导节点做一些自动化的操作，限制在节点这一层就够了，如果一是一个flow被部署在了一个高权限节点，那么就代表用户是接受高权限执行的代价的

确认权限边界在节点层。Flow 指导承载节点进行自动化操作，使用该节点的权限，不再为每条 Flow 单独配置资源或操作权限。将 Flow 部署到高权限节点，代表用户接受以该节点高权限执行的代价。

明确拒绝助手提出的逐 Flow 限权建议，撤回由此派生的 per-Flow scope、授权配置和隔离要求；不能以默认安全策略为由重新加入。本决策针对权限，不扩展为取消已有资源契约校验，也不构成对任何具体操作的独立执行授权。依赖 P07 的节点与功能组合模型。

### P09 — 资源包含自身操作，额外能力由节点以命令资源提供

用户主动重新定义资源概念，并回答外部服务接入边界。原文：

> 我重新定义一下资源的概念
> 比如平台内部提前定义的好的，比如变量，变量的读取和订阅是一个整体是属于变量这个资源概念的一部分，也是整个网络定义的一部分；还有一个专门的命令资源，是节点额外提供能力，所以是一种额外的命令资源
>
> 所以比如会有一个节点通过发邮件的命令，就是调用这种命令资源，flow理论上也可以调用平台内的其他资源，完成可拓展的组织
>
> 然后回答你的问题，Flow 需要调用尚未接入的外部服务时，是否必须先把相应能力封装成节点资源？
> 是的，只有节点可以提供资源，不能有游离在整个网络体系之外的指令

确认的概念与边界：

- 平台预定义的资源类型具有完整语义；变量的读取与订阅属于变量资源本身及网络定义，不应为了被 Flow 使用而拆成独立命令资源。
- Command 是专门的命令资源类型。节点额外提供的能力可以作为该类型的资源，例如某节点提供发邮件命令。
- Flow 可以组织命令资源，也可以使用平台内的其他资源，不能收窄成只编排 Command。
- 只有节点可以提供资源；外部服务须先由节点以资源形式接入，不能存在游离在网络体系之外的指令。
- P08 保持：Flow 仍按承载节点权限执行，不增加逐 Flow 授权。

P09 回答时，节点开发者能否定义新资源类型仍待确认；该问题随后由 P10 解决。已查阅当前 `resource-platform-v2`：现行规范允许资源类型扩展，变量操作归属变量，Command 提供 invoke。

### P15 — Flow 独立资源类型、动态部署与触发绑定

上一轮助手建议将 Flow 的入口发布为 Command；用户给出了替代定义。原文：

> flow单独作为一种资源吧，因为这种是一种动态部署的，和命令相对固定的不一样，当然调用方式可能类似，并且flow应当是可以绑定触发条件的，比如某个变量被修改成了某值，某个事件发布了之类的

确认：

- Flow 单独作为一种 Resource type，由节点提供，依赖 P09/P10，不新增游离于节点/资源体系的对象。
- Flow 具有动态部署的产品特征；Command 是节点相对固定的能力。保留“相对固定”原意，不推断所有 Command 永久不可变或只能静态注册。
- 撤回“将 Flow 归为 Command Resource 对外提供”的候选建议。调用方式可能类似，但这不意味着两种资源类型合并；精确调用 capability、输入输出和生命周期仍待设计。
- Flow 可以绑定触发条件，明确包括变量被修改成某值、某个事件发布等来源；示例不是穷尽的触发类型列表。
- 持久状态、重启恢复、节点权限和内嵌语言引擎等已确认原则保持有效。

尚未确定触发条件在代码或独立配置中的表达、初次订阅快照是否触发、重复事件与断线后的处理及部署接口。每次执行的记录模型见 P16，默认调度策略见 P17，Run 的版本绑定见 P18。

### P16 — 每次触发形成可追踪的 Run

问题：每次满足触发条件后，是否应形成可单独追踪的一次执行（Run）？上一轮建议同时区分 Flow 与 Run：Flow 资源保存程序、触发配置和声明的持久状态；Run 记录本次触发来源、输入、执行状态和结果，作为 Flow 内部执行记录，不新增网络基本对象。

### 推荐集成方向

以下为回答用户问题的候选框架，不是可执行架构计划或已定稿接口：

1. 在普通节点装配时可选地加入 Flow 组件，组件内部嵌入语言引擎。独立 Flow 产品也通过同一组件装配普通节点；支持与其他节点能力集成，遵循 P07。

4. Flow 宿主负责接收事件、调度脚本、处理异步资源结果、取消、错误及执行状态。引擎运行上下文按其并发约束使用；各脚本的运行数据分开管理，但共享承载节点身份和权限，不增加 P08 已拒绝的逐 Flow 授权。
5. 持久状态置于引擎外的节点存储，以定义 ID、代码版本与状态版本关联。重启时重建引擎、加载相容定义、恢复已声明状态并重建可恢复的触发/等待。事件处理入口式恢复是候选方式；不能据此承诺任意代码行、闭包、调用栈或普通定时器恢复。
6. 操作结果不确定时，记录并依 P06 暂停解释；保存计数与远端邮件发送之间不存在天然跨节点事务，不能通过简单地重新运行脚本保证不重复发送。重连 gap 同样须有明确处理。
7. P15 已明确 Flow 自身采用独立资源类型并支持动态部署和触发绑定。其管理、调用和观察通过该节点资源表达；精确操作及内部记录组织仍待设计。旧示意代码中的触发注册 API 不冻结触发配置应写在何处。
