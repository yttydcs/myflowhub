# 2026-03-28 SDK v0.1.13 下游依赖收口

## 变更背景 / 目标
- `MyFlowHub-SDK v0.1.13` 已经发布，但直接消费方仓库仍停留在 `v0.1.12`。
- 这会导致：
  - 单仓 `GOWORK=off` 构建时仍解析到旧 SDK patch
  - Android 的本地 `replace` 语义继续掩盖 semver 基线偏旧的问题
  - 后续继续发应用层 patch 时，发布说明和真实依赖链不一致
- 本次目标：
  - 把 `MyFlowHub-Win`、`MyFlowHub-MetricsNode`、`MyFlowHub-Android/hubmobile` 的 direct SDK 依赖统一到 `v0.1.13`
  - 保持改动范围严格停留在 `go.mod/go.sum`
  - 用 `GOWORK=off` 完成真实依赖解析验证

## 经验 / 教训摘要
- 上游 SDK 已经发布新 patch，不代表下游 direct consumers 会自动完成收口，仍需要逐仓 bump `go.mod/go.sum`。
- Android 即使继续保留 `replace`，也必须同步提升 `require` 的 semver 基线，否则本地和远端发布语义会继续漂移。
- `MetricsNode/windows` 的 `frontend/dist` 前置条件依旧只是验证约束，不应被误记成依赖升级本身的问题。

## 可复用排查线索
- 症状
  - `go list -m github.com/yttydcs/myflowhub-sdk` 仍解析到旧 patch
  - Android `hubmobile` 本地测试通过，但 `go.mod` 仍停在旧 SDK 版本
  - `pattern all:frontend/dist: no matching files found`
- 触发条件
  - 上游 SDK 刚发布 patch，但应用层仓库未同步 bump 依赖
  - Android 使用 `replace ../../MyFlowHub-SDK`，本地 sibling 路径掩盖了 semver 偏旧
  - `MetricsNode/windows` 在未准备 `frontend/dist` 时直接执行 `go test`
- 关键词
  - `GOWORK=off`
  - `go list -m`
  - `myflowhub-sdk v0.1.13`
  - `replace ../../MyFlowHub-SDK`
  - `frontend/dist`
- 快速检查
  - 对每个 direct consumer 执行 `GOWORK=off go mod tidy`
  - 再执行 `GOWORK=off go list -m github.com/yttydcs/myflowhub-sdk`
  - Android worktree 下若 `replace` 目录失效，临时补 sibling junction 后再验证
  - `MetricsNode/windows` 测试前先准备临时 `frontend/dist/placeholder.txt`，测试后删除

## 关键设计决策与权衡
- 采用“只升级 SDK patch，不碰业务代码”的最小方案：
  - 这轮目标是 semver 收口，不扩大成额外的功能或依赖治理工作。
- Android 继续保留现有 `replace`：
  - 当前开发和 CI 都依赖 sibling checkout，顺手移除 `replace` 会把范围扩大成发布策略重构。
- `MetricsNode/windows` 的 `frontend/dist` 只临时补齐：
  - 用于满足 `go:embed` 前置条件，测试结束后立即删除，不把占位目录带入提交。

## 潜在影响与回滚方案
- 潜在影响
  - 这轮只提升 SDK patch，不涉及协议或运行时逻辑变化；主要影响是下游会解析到最新 SDK 发布内容。
  - Android 本地和 CI 仍会优先消费 sibling `replace` 目标，本轮只是让 semver 基线与当前实现保持一致。
- 回滚方案
  - 对各消费方仓库：
    - 回退本轮依赖升级提交
    - 或把 `go.mod` 中的 `myflowhub-sdk` 恢复到 `v0.1.12` 后重新执行 `go mod tidy`
  - 对已发布 tag：
    - 不删除、不改写 `v0.1.13`
    - 若发现问题，通过更高 patch 修复
