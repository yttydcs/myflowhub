## 关键设计决策与权衡
- 采用 `Server -> SDK -> Android` 的顺序收口，而不是三仓同时修改。
  - 原因：Android 同时依赖 Server 与 SDK，最后处理最容易定位问题。
- 本次只做版本升级，不改运行时逻辑。
  - 原因：`Core v0.4.0` 的兼容性已由上游 workflow 验证，本轮目标是版本闭环而不是功能开发。
- Android 保留本地 `replace` 策略，并将 `SDK` 纳入同类本地 replace。
  - 原因：Android 仓当前本就依赖同级 `Server` 仓进行 meta-workspace / CI 联调。
  - 权衡：继续保持“依赖同级仓”的开发态构建方式，而不是单仓独立构建；但这与现有仓库使用方式一致，维护成本更低。
