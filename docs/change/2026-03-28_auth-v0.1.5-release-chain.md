## 经验 / 教训摘要
- `go.work` 联调通过，不代表 submodule 的 `go.mod` 最低版本就是正确的。
- 对 `MyFlowHub-SubProto/auth` 这类子 module，除了检查“上游 tag 是否已发布”，还要检查“module `go.mod` 是否已经声明了当前源码真实需要的最低 `Core/Proto` 版本”。
- 发布顺序仍必须按依赖方向执行：`Proto/Core` 基线就绪 -> `auth` 发 tag -> `Server` 升级消费 -> `GOWORK=off` 全链验证。

## 可复用排查线索
- 症状：
  - `MyFlowHub-SubProto/auth` 在本地 workspace 正常，但 `GOWORK=off go test ./...` 失败
  - 常见错误：
    - `undefined: protocol.ActionAuthorityPolicySync`
    - `undefined: protocol.ActionListRegisterPermits`
    - `undefined: protocol.ListRegisterPermitsReq`
    - `undefined: coreconfig.DefaultAuthBootstrapFirstRegisterRole`
- 触发条件：
  - 子 module 新增了对 `Proto/Core` 新符号的引用
  - 但 `go.mod` 仍保留旧的最低依赖版本
- 关键词：
  - `GOWORK=off`
  - `ActionAuthorityPolicySync`
  - `ActionListRegisterPermits`
  - `DefaultAuthBootstrapFirstRegisterRole`
  - `minimum version drift`
- 快速检查：
  - 先在目标 submodule 下执行 `GOWORK=off go test ./... -count=1 -p 1`
  - 再检查 `go.mod` 的 `Core/Proto` 最低版本是否覆盖当前源码引用的符号
  - 发布 tag 后再到下游执行 `GOWORK=off go list -m` 与 `go test`

## 关键设计决策与权衡
- `MyFlowHub-SubProto/auth` 采用“最小依赖声明修正 + patch 发版”，而不是并入其他功能或继续拖延到更大版本一起处理。
- `MyFlowHub-Server` 采用“只升级 auth 版本、不改业务逻辑”的最小消费策略，减少回归面。
- lessons 只更新已有 `cross-repo-semver-release`，不新建独立 lesson，避免重复沉淀同一类发布链问题。
