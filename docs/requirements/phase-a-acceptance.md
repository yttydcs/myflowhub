# A 阶段验收标准

更新：2026-10-19。版本：A-AC-v1。状态：P20—P33 全部确认，含 2000 个活动标准变量各每秒更新一次及 R1 全部建议；这是产品验收定稿，尚未实施或执行本页验收。实施拆解见活动工作树的 plan.md / review.md。

## 已确认范围与主场景

P20 选择 Windows 资源操作阶段版，先完善 Hub、Desktop、Metrics 的基础能力，新 Flow 后续推进；保留既有产品模型与产品独立性要求。

P21 确认主场景：技术用户从干净环境开始，在真实跨设备网络中部署产品、完成节点准入和明确授权；Desktop 发现 Metrics 并持续查看真实指标；手动修改一个获授权的设备状态并回读实际结果；撤权后明确拒绝操作，断网与重启后按预期恢复，身份、配置和视图保留。

来源与原话：[P20/P21 及当前讨论](../intake/2026-09-06_product-definition-grill.md#p21--确认-a-的主验收场景)。整体产品定义见[统一产品定义](product-definition.md)。

设备数量、部署及传输由 P23 确认，入口由 P22、交付由 P24、系统由 P25、控制组由 P26、正常量化由 P27、失败由 P28、撤权由 P29、网络恢复由 P30、重启及保存边界由 P31 确认，见下文；所有产品门槛已由 P33 收束；实际构建号、包格式和测量工具在实施规划/执行中落实。恢复不等同于断网操作必定成功、零事件丢失或不确定写入自动重试。

## 验收基线

以下为已确认主场景的检查总览，具体门槛以本页后续条款为准。采用既有准入、授权、标准变量、产品独立性及数据保护合同；本页确定验收结果，具体 wire/API 技术设计由实施计划管理。

| 准入与授权 | 节点具有各自身份；入网后只获得明确授予的业务权限；授权和拒绝均可验证 | 最小授权集与凭证交付方式；准入和授权管理可用命令行 |
| 发现与读取 | Desktop 能在获授权范围发现目标节点和资源，读取平台标准定义与真实值；空、加载、拒绝、不可达等状态可区分 | P23 拓扑，P26 资源，P27 时限，P33 规模与完整证据 |

| 手动控制与回读 | 对设备 B 的系统主音量与静音完成标准写入；设备实际变化、owner 确认结果与重新读取一致；本地修改自动更新至 Desktop；最终恢复初始状态 | P27 数值/时限，P28 失败/等待，P29—P31 撤权与中断/重启，P33 并发/实例替换 |
| 撤权 | P29 已确认：新访问按撤销权限由服务端拒绝，已有订阅/界面最多 3 秒收束；保留布局与草稿，旧值失效，重新授权后不自动提交 | 已确认，具体证据与测试实施随后规划 |
| 断网与重启 | P30 已确认 5 秒检测/10 秒网络恢复，P31 已确认独立进程重启后 15 秒恢复已保存状态及订阅，未保存内容正常退出需提示 | 已确认；实际环境及实现证据在后续验证落实 |
| 通用扩展 | 一个新增节点提供的标准资源可被发现和操作，无需修改平台核心或增加 Metrics 专用展示逻辑 | P33 六类型、至少布尔/数字可写，源码/说明/示例包及通用接入证据 |

运行中不改变某一产品的身份或状态来绕过问题，不使用假数据证明真实设备能力；具体用例使用隔离配置并明确实际环境。本表不自动增加全网搜索、实时拓扑推送或细粒度成员权限等延期能力。

## 已确认标准：操作入口（P22）

首次部署、准入和授权管理可以用命令行；日常查看和控制通过界面完成。该选择由用户明确确认，来源见[P22 原话](../intake/2026-09-06_product-definition-grill.md#p22--首次部署准入及授权管理可用命令行日常查看与控制使用界面)。

验收应遵守这一边界，不能要求用户用命令行代替正常的日常查看和控制。允许命令行管理不代表必须新增图形化部署或授权管理入口；具体命令、配置资料和错误说明按 P24/P33 交付，由规划落实。

## 已确认标准：参考环境与部署拓扑（P23）

用户确认采用以下跨设备基准：

- 两台真实 Windows 设备，位于同一局域网，通过 TCP 连接。
- 设备 A 运行 Hub 与 Desktop，设备 B 运行 Metrics。
- Desktop 和 Metrics 各自作为普通节点直接接入 Hub，使用各自独立身份、进程和状态；通过明确授权验证跨节点资源操作，同机运行的 Hub/Desktop 不产生额外权限。
- 按 P21 从干净环境和新建的隔离验收配置开始；交付基线由 P24、Windows 11 x64 范围由 P25 确认，实际系统构建号、控制对象和量化指标仍待决定。

该基准覆盖真实设备之间的发现、读取、控制、中断与恢复，只约定阶段验收环境，不限制产品长期的拓扑、部署形态或传输能力。用户原话见[P23](../intake/2026-09-06_product-definition-grill.md#p23--确认两台-windows-设备的局域网-tcp-验收部署)。确认环境不表示两台设备已就绪或已经完成真实环境验收；具体 Windows 版本及硬件另行核实。

## 已确认标准：独立可运行包与完整部署说明（P24）

用户确认 A 以独立可运行的发行包加完整部署说明作为部署验收输入，安装向导和自动更新后续再做。该选择包含上一轮提出的交付基线：

- Hub 包提供命令行程序与必要管理工具；Desktop 与 Metrics 各有自己的可运行包，能够独立启动，不强制安装另一产品。
- 用户无需安装 Go、Node.js 或其他开发工具链，也无需编译源码即可部署；所需系统运行依赖须明确列出，提供检查与安装说明，不承诺没有任何系统依赖。
- 提供清晰版本标识、校验信息、无真实凭据的配置示例，以及按 P23 拓扑部署、按 P22 完成准入与授权的可重复操作说明；配置和凭据遵守既有产品隔离要求。
- 安装向导与自动更新后续再做；独立升级、回滚、卸载与状态保留按下文 P33 定稿执行，不因使用可运行包而免除。

来源与原话见[P24](../intake/2026-09-06_product-definition-grill.md#p24--确认独立可运行包与完整部署说明安装向导及自动更新后置)。交付原则已确认，Windows 11 x64 范围随后由 P25 确认；具体压缩格式、目录、服务安装机制和实际系统构建号仍待细化，本次没有生成交付包、执行验收、创建发布或批准实施。

## 已确认标准：Windows 11 x64 验收范围（P25）

用户确认 A 先以 Windows 11 x64 作为正式验收范围，Windows 10 和 ARM64 后续再评估。两台设备记录实际系统版本、构建号、处理器架构及运行依赖版本，按 P23 布局使用 P24 交付包完成验收。

来源与原话见[P25](../intake/2026-09-06_product-definition-grill.md#p25--确认-windows-11-x64-正式验收范围)。该架构与当前 Desktop/Metrics 构建目标 `windows/amd64` 一致，但选择范围和已有构建均不代表完成真实设备验收或所有 Windows 11 构建均已验证；实际硬件、构建号和可用性仍待核实。

## 已确认标准：系统主音量与静音控制（P26）

用户确认以设备 B 的系统主音量和静音作为首个控制组，从设备 A 的 Desktop 通用变量界面操作设备 B 的 Metrics 资源，覆盖数值与布尔两种标准写入：

1. 读取并记录设备 B 原始音量与静音状态，确认目标为本次验收设备的实际音频输出。
2. 修改一次音量、切换静音；通过设备 B 的 Windows 系统状态核对实际变化，结合 owner 确认值、重新读取结果及订阅更新判断一致性，不能只观察 Desktop 控件自身变化。
3. 在设备 B 本地更改同一状态，验证 Desktop 通过订阅显示变化，不依赖用户手动刷新。
4. 验收结束恢复初始音量与静音状态，并核对恢复结果；不要求播放声音。

来源与原话见[P26](../intake/2026-09-06_product-definition-grill.md#p26--确认系统主音量与静音验收组)。当前 Metrics 已提供标准音量/静音写入，既有统一变量归档记有音量写入与恢复证据；该历史证据不证明本次双设备验收通过。取值、容差及正常响应时间由 P27、请求最大等待和结果不确定规则由 P28 确认；无可用音频设备时按 P33 记 Unavailable，必验项不得算通过。本次没有执行实际控制。

本控制组不冻结系统 API 或资源路径，也不将亮度等其他控制的真实硬件验收视为已经通过。

## 已确认标准：取值、容差与正常响应时间（P27）

以下数值已由用户确认作为 A 正常操作的验收标准，来源见[P27](../intake/2026-09-06_product-definition-grill.md#p27--确认-a-正常操作的取值容差及响应时间)。确认门槛不代表现有实现已经实测达标。

| 项目 | 已确认数值与口径 |
| --- | --- |
| 音量取值 | 依次设置 20%、40%，每次完成确认和独立回读后再进行下一次，最后恢复原始音量 |
| 静音取值 | 分别设置 true、false，每次确认并回读，最后恢复原始静音状态 |
| 音量目标容差 | 实际系统主音量与目标相差不超过 1 个百分点；目标 20% 时允许 19%—21%，不是相对误差 1% |
| 反馈一致性 | owner 确认值、独立回读及 Desktop 已确认展示应表达同一个实际值；音量目标容差不允许它们长期互相矛盾；静音布尔值必须精确一致 |
| 采样间隔 | 本次音量/静音验收均设置为 1 秒，记录实际配置，避免更长采样周期与同步门槛冲突 |
| A 远程写入 | 从 Desktop 触发有效提交起，到设备 B 系统状态经确认、A 收到成功反馈且一次独立回读一致，不超过 2 秒；不把输入编辑停留时间计入 |
| B 本地修改同步 | 从设备 B 系统状态实际改变起，到 A 的 Desktop 通过订阅显示该实际值，不超过 3 秒，无需手动刷新 |

这些时间门槛适用于 P23 的正常连通局域网、目标资源可用且无其他并发修改的场景；撤权、断网、重启及并发写入单独定义。超过正常门槛即该次正常响应检查不通过，不能通过延后反馈、把草稿当确认值或自动重试掩盖；最大等待及反馈不确定规则随后由 P28 确认，正常 2 秒门槛不自动等于协议超时。

测量需覆盖系统实际状态与标准资源结果，不以人眼估计或两台机器未校准的墙上时钟差作为唯一证据；后续验证方案应采用统一计时观察者或可校准的关联记录。计时口径已明确，不冻结验证实现。恢复原始状态的值核对沿用上述容差与布尔精确匹配；实际检查与恢复均未执行。

数值依据：当前 Metrics 声明音量/静音默认采样间隔 1,000 ms，Windows adapter 以 0—100 整数百分比校验并四舍五入读回音量，静音为真实布尔。P27 已确认 1 秒采样、1 个百分点容差及 2 秒/3 秒门槛；这些是验收要求，不由默认采样值自动推导为已保证性能。

## 已确认标准：写入失败、等待上限与结果不确定（P28）

用户确认以下整套失败处理规则，包括 5 秒最大等待、不自动重试和不离线补发写入，来源见[P28](../intake/2026-09-06_product-definition-grill.md#p28--确认失败处理5-秒等待及不自动重试补发写入)。不伪报成功、保留草稿及不自动重试继续遵守既有标准变量边界。

| 情况 | 已确认行为 |
| --- | --- |
| 明确拒绝或确定未执行 | 展示具体原因和未执行状态，保留输入；已有明确错误时直接结束等待，不等满 5 秒 |
| 可能已发出，5 秒内仍无可靠终态 | 从有效提交起最多等待 5 秒，结束加载并标记“结果不确定”；不能把没有收到确认解释为设备一定没执行 |
| 写入已确认成功，但后续回读失败 | 保留已知的写入确认，另行提示当前值未核实/回读失败；不能篡改为确定未执行，也不把草稿当当前真实值 |
| 恢复与重试 | 不自动重试写入、不离线排队待发；用户输入、最后已知真实值及其有效性分别表达。权限允许时先刷新/回读；用户明确再次提交时重新校验资源实例、当前修订及权限 |

正常验收仍要求 P27 的 2 秒内完成确认与回读；超过 2 秒的正常响应检查已经不通过，5 秒只限定无可靠结果时的用户等待，并非把正常门槛放宽至 5 秒。5 秒结束等待不保证远端操作回滚或绝不迟到执行，不能依此立即重复发出可能已执行的写入。

回读达到目标值可以更新当前状态，但单凭数值相等不能证明原请求一定执行成功。后续若取得可关联的可靠结果，应保留原请求身份并核对会话和资源实例，不能让旧会话的迟到结果覆盖新状态。A 的具体请求取消/期限传递与测试方式需在设计时落实，不在本次讨论中修改实现。

## 已确认标准：撤权与重新授权（P29）

用户已确认整套撤权标准及 3 秒上限，来源见[P29](../intake/2026-09-06_product-definition-grill.md#p29--确认撤权标准及-3-秒状态切换上限)。在 P23 正常连通环境中，使用独立管理主体在线撤销 Desktop 对 Metrics 音量/静音资源的有效业务权限。管理操作返回成功、对应权威策略已提交，作为撤权确认点；不能仅删除一个被其他 Grant/Binding 重复授予的权限就认定已收回访问。

| 检查 | 已确认通过条件 |
| --- | --- |
| 仅撤销 write | 确认点后新发起的写入必须由服务端拒绝，设备不因这些被拒绝请求改变；原本仍获授权的读取/订阅继续工作。即使控件暂时可见或客户端保存了旧描述，也不得绕过服务端权限 |
| 再收回 read/subscribe | 确认点后新读取和新订阅均拒绝；不再接收确认点后产生的受保护新值。已有订阅结束或失效，Desktop 最多 3 秒内显示无权限或失效状态，不能继续标为实时 |
| 界面与数据保护 | 保留 View 布局与草稿；最近已知值可以保留，但标记失效，不伪造为当前值。已知无权后禁用相应提交，禁止自动发送旧草稿 |
| 重新授权 | 可通过用户刷新/重建订阅取得最新状态，重新核对实例、修订和权限；旧草稿不自动提交，实际再写由用户明确确认 |

3 秒只限定客户端订阅/界面状态收束，不是服务端允许新请求继续访问的宽限期；排队中、链路中已有旧事件需与确认点后产生的新值区分。验收应核对实际设备和资源结果，按钮是否灰掉不足以证明权限生效。

撤权确认点前已被授权接受并进入执行的写入不承诺回滚，按 P28 可靠结果如实表达；新写拒绝场景应与已有在途写入单独验证。该标准不引入全局权限发现或 payload/member 策略设计，本次未修改实现或执行真实撤权验收。

## 已确认标准：断网检测与自动重连（P30）

用户确认 5 秒断网识别、网络实际恢复可达后 10 秒自动恢复，并要求后续调整重连参数及验证，来源见[P30](../intake/2026-09-06_product-definition-grill.md#p30--确认-5-秒断网识别与-10-秒自动恢复)。在 P23 的两台设备均运行、Hub 服务正常、身份配置和授权保持有效的前提下，分别中断 Desktop—Hub 与 Metrics—Hub 的网络路径，再恢复双向连通。测试包含连接明确关闭和静默丢包，不把主动关闭 socket 的结果当作静默断网检测已通过。

| 检查 | 已确认门槛与结果 |
| --- | --- |
| 断网检测 | 从网络中断生效起最多 5 秒，Desktop 将受影响资源标为断连、陈旧或不可用，并禁止向其提交；不能把 Metrics 离线误报成 Desktop 与 Hub 必定断连 |
| 中断时数据与写入 | 保留 View、草稿和最近真实值，标明失效；已经发出的写入按 P28 判定，不自动重试、不离线排队；不伪造当前值或成功结果 |
| 自动重连与订阅恢复 | 从 Hub 端口与相关双向网络实际恢复可达起最多 10 秒，自动重建合法连接、取得最新快照并恢复订阅，无需用户重启应用或手动刷新 |
| 恢复后的状态 | 重新确认资源实例、修订及权限，禁止旧会话迟到结果污染新状态；旧草稿不自动提交，需要再次写入时由用户明确确认 |

5 秒检测与 10 秒恢复是已确认验收要求，不是现有已实测性能；10 秒从实际网络可达起计，不从应用已经重连成功后才起计。若权限被撤销、身份失效或 Hub 未恢复健康，应明确报告对应原因，不套用正常恢复成功标准或自动扩大权限。

恢复要求取得最新值，不承诺回放断网期间每次变量变化；如存在事件缺口，沿用已有 gap/有效性语义，不伪装成连续无损更新。长期中断的重试仍须有界，不形成忙循环；具体重试参数由后续技术设计落实。

实现约束：当前通用 ParentSupervisor 的默认最大退避为 30 秒（`runtime/node/supervisor.go`），仅靠默认值不能保证已确认的 10 秒恢复要求。后续实施必须检查产品重连配置并按验收目标调整、验证，P30 已明确保留这一要求；本轮不修改参数，也不将订阅重建误当成持久事件回放。

## 已确认标准：独立进程重启与已保存状态恢复（P31）

用户确认整套独立进程重启标准、15 秒恢复上限及已保存状态边界，正常退出时提示未保存内容，原话见[P31](../intake/2026-09-06_product-definition-grill.md#p31--确认-15-秒重启恢复及已保存状态边界)。分别验证 Hub、Desktop、Metrics 的正常退出后重启与强制终止后重启，每次只重启一个进程，其他产品进程继续运行。允许用户重新启动目标交付程序，不要求本项新增进程守护、开机自启或操作系统重启恢复机制；手动重新启动等待时间不计入恢复耗时。

验收使用同一 Windows 用户、同一状态目录及已经保存的有效配置，Hub 网络可达、原有身份/授权仍有效；Desktop 使用已保存且仍为 active 的有效 Profile，不覆盖用户此前主动返回 Profile 选择或退出连接的意图。

| 重启对象 | 已确认保留与恢复结果 |
| --- | --- |
| Hub | NodeID、密钥、准入状态及已成功保存的授权策略保留；原 Desktop/Metrics 无需重新准入或重新配权，能恢复合法连接及订阅 |
| Metrics | NodeID、受信任父节点、采集/可写性/间隔等已保存配置保留；重新采集当前真实值，不重放上次控制或用旧缓存回写设备 |
| Desktop | Profile、受保护凭据、已保存 View 布局与设置保留；无需重输 Permit/重新准入，按原 active Profile 恢复连接，显示最新值并重新订阅 |

从目标进程实际重新启动起最多 15 秒，使受影响的 Desktop 资源重新取得最新快照并恢复订阅；包含该目标进程的初始化时间，不从初始化已经结束才起计。Hub 恢复可达后的网络重连仍须满足 P30 的 10 秒门槛，两者不互相替代。依赖损坏、凭据/授权失效时应明确失败，不生成替代身份或静默清空状态绕过。

已确认保存边界：跨进程恢复已成功保存的持久状态；Desktop 未提交草稿及未保存布局不要求跨进程恢复，正常退出有未保存内容时需提示并允许取消。Hub/Metrics 重启而 Desktop 仍运行时，保留 Desktop 的布局和草稿，但重新检查资源实例、修订和权限，禁止自动写入；不把这一会话内保护扩大为草稿持久化承诺。

重启过程中在途写入继续遵守 P28；程序重新启动不重试、补发或重放旧写入，旧会话迟到结果不能覆盖新状态。上述重启方式、保存边界与 15 秒上限已确认；本轮未启动/终止实际进程，也未改变当前状态格式或产品行为。

## 补充验收标准定稿（P33）

来源：[P33 原话与确认范围](../intake/2026-09-06_product-definition-grill.md#p33--验收标准定稿并进入实施规划)。本节由 R1 草案收束为已确认标准，P20—P31 的条件、数值与禁止行为保留；历史测试不充当新候选验收已通过。

### 1. 并发冲突与资源实例替换

沿用当前标准 Variable 的条件写入与实例隔离契约，不新增合并、抢占或自动重基策略。

| 场景 | 已确认通过条件 |
| --- | --- |
| 两个消费者基于同一修订写不同值 | 使用可控标准变量固定初始修订，暂停无关采样发布后同步提交；仅一个成功，另一个明确冲突，最终值等于获确认的成功结果，业务写入处理只执行一次 |
| Desktop 草稿期间他方修改实际值 | 更新的真实值与旧草稿分别表达，显示冲突，保留草稿，不静默覆盖或自动套用到新修订；用户刷新并明确再次提交后才可写入 |
| 仅采样时间或质量更新，实际值未变 | 按现有契约推进可用修订并保留草稿，不把纯采样刷新误报为值冲突；不可用或撤权仍须禁用提交 |
| 同一 owner/名称注销后重新注册 | 新实例与旧实例可区分；旧实例请求、草稿和迟到响应不得写进或覆盖新实例；View 引用可保留，操作恢复须取得新实例定义和状态、重新明确编辑意图 |

并发和实例替换两类各重复 20 轮，零错误覆盖、零跨实例误写、零被拒绝请求触发业务写入。可用 Desktop 加 SDK 测试消费者形成两个逻辑客户端，不要求新增第二台 Desktop 产品或第三台物理设备。

并发竞态使用独立测试变量，以便证明同一初始修订下的正确性；真实 Metrics 仍按 P26/P27 单独核对实际设备。若未固定修订且采样恰好抢先更新，两次请求都冲突可能是正确结果，不能用这个不受控场景宣称“必须恰好一个成功”。

### 2. 稳定性、规模与重复恢复

本阶段采用可在两台参考设备上复现的基础稳定性门槛；CPU 与内存配置、系统构建号和运行依赖版本全部记录，不虚构统一硬件。

| 项目 | 已确认通过条件 |
| --- | --- |
| 正常稳定运行 | 预热 10 分钟后，连续运行 2 小时；网络健康、身份授权有效，无计划故障注入 |
| 参考规模 | 按 P32 提高到 2000 个标准 Variable，要求单个 Desktop 客户端真实保持 2000 个活动订阅，全部纳入可浏览、查看和按权限操作的展示范围；按 P33 每个每秒更新一次（约 2000 次变量更新/秒）验收，其中含真实 Metrics 音量/静音，其余可用明确标注的负载提供者，不以生成数据证明硬件能力 |
| 正常写入检查 | 2 小时内分散执行至少 100 次串行合法写入，每次使用最新有效修订，按 P27 检查响应和真实结果；负载写入可用测试变量，真实音量/静音仍须独立覆盖并恢复初值 |
| 正常运行错误 | 零意外崩溃、死锁、身份/已保存配置损坏、越权或跨实例误写；健康条件下的正常操作不得出现未解释失败，已有 P27 时限逐次检查，不能只用平均数或百分位掩盖失败 |
| 内存增长 | 对每个产品及其专属子进程采集私有提交内存；比较预热后首 10 分钟与结束前 10 分钟的中位数，增长不超过 max(基线的 25%, 64 MiB)。记录进程归属及采样口径，避免共享子进程重复计数；这是已确认验收预算，不是当前实测结论 |
| 连接与订阅清理 | 故障用例结束并恢复稳定后，连接/订阅/待处理请求回到该场景预期基数；不遗留重复订阅或失效会话，不出现可复现的持续累积 |
| 重复故障恢复 | 与正常 2 小时运行分开进行；P29 撤权/重新授权、P30 两条路径的明确断连/静默丢包、P31 三产品的正常退出/强制终止重启，每种已定义场景各重复 5 次，全部满足各自已确认门槛 |

故障注入期不混入正常响应时间统计，但必须逐次满足对应故障恢复规则。内存采样和诊断工具留给验证方案落实，不要求新增面向用户的监控产品；CPU、句柄与错误趋势保留诊断曲线，暂不额外提出缺少统一硬件依据的 CPU 百分比硬阈值。

P32 的数量要求承接原草案“同时订阅并展示”的口径，不能只注册 2000 个目录条目而只订阅可见的少数资源。界面可采用虚拟化、按需渲染等实现方式，不要求同时创建 2000 个实际控件节点，但不得因此减少应验证的活动订阅或令未显示变量停止接收更新。2000 是总量目标，具体 owner 分布、值类型/大小和参考硬件在规划中明确并记录，不擅自解释为每个 owner 均须提供 2000 个或每个变量使用协议最大载荷。

数量放大不自动放宽 P27—P31 的既有正确性、正常操作与恢复门槛；应在最终参考负载下检验，不能仅用空闲环境时限充当规模验收。P33 已整体确认 2 小时、每秒更新一次、100 次写入、故障轮数和内存增长预算。

规划前源码核对发现直接约束：Desktop 订阅桥上限 256（`apps/desktop/subscriptions.go`）；`runtime/subscription/manager.go` 通用管理器默认最大订阅 1024；Desktop 前后端单 View 控件上限均为 64（`apps/desktop/frontend/src/workspace-layout.ts`、`apps/desktop/views.go`）；catalog 当前受单次 payload 预算约束（默认 1 MiB）。这些是后续必须评估和解决的容量缺口，不能用当前默认值宣称 2000 已支持；目录序列化大小、批量建订阅、队列/背压及 UI 更新成本亦需验证。应保持有界资源模型，不简单取消所有上限或静默截断结果。本次定稿不修改代码或扩容参数；规划负责给出有界扩容方案和验证任务。

### 3. 独立升级、回滚、卸载与版本兼容

以两个真实可复现的相邻版本 N（最终候选）与 N−1（指定回滚基线）验证。它们须使用相同的网络协议和本地状态主版本，并属于当前标准 Variable 契约；不能拿已退役旧变量协议或同一二进制改版本号充当升级/兼容证明。

基线版本和源码提交在规划中指定并记录；若尚无发布版，可使用符合当前契约的实际历史提交构建基线。主版本不兼容时明确拒绝并说明原因，不静默降级、清空身份或猜测转换；跨主版本迁移不纳入此相邻兼容窗口。

| 项目 | 已确认通过条件 |
| --- | --- |
| 包与运行独立 | Desktop-only、Metrics-only、同机共存三种形态均可运行；各有独立身份、状态根和进程，删除/更新其中一个不会直接终止另一个或改动其状态。同机共存是补充隔离用例，不替代 P23 两设备主验收 |
| 混合版本 | Hub、Desktop、Metrics 各取 N 或 N−1，共 8 种组合，分别通过基本连接/准入状态、读取、订阅和一次获授权控制烟测；完整稳定性与故障矩阵在最终 N/N/N 候选上执行 |
| 手动升级 | 仅停止目标产品，按说明保全其专属状态、替换程序包后启动；NodeID、密钥、信任、准入、授权及已保存配置/View 按职责保留；重新运行满足 P31，其他产品继续运行并按中断规则显示目标可用性 |
| 手动回滚 | 支持窗口内旧版能读取新版已保存的同主版本状态，回滚后保留身份、已保存配置/视图及最新有效的准入和权限状态；不通过恢复过期策略备份来静默复活已撤销权限。无法安全读取时必须阻止回滚并说明，不声称无损回滚通过 |
| 备份与数据保护 | 提供产品专属状态备份/恢复说明，敏感状态按原保护方式保存，不进入公开证据；备份不免除相邻兼容承诺，也不是丢弃升级后授权变化的捷径 |
| 移除程序包 | 停止并移除该产品的程序文件，默认保留其独立状态目录；重新部署后可恢复身份与已保存状态，不要求重新准入 |
| 显式清理状态 | 单独、明确的清理步骤及后果说明，只清理目标产品；不会删除另一产品或 Hub 的身份/策略。清除本地身份不等于撤销网络中的准入，后者通过既有管理流程单独处理 |

安装向导与自动更新继续按 P24 后置。本组不要求联网更新服务或包管理器；目录、文件复制和备份格式属于实现细节，但文档应让技术用户可重复操作。升级/回滚中的手工等待不计入 P31，从目标进程实际启动起仍满足已确认恢复标准。
