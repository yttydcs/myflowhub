# MyFlowHub 统一产品定义

更新：2026-10-19。本文保留既有产品需求、架构决策和 P01—P19 已确认结论，并追加 P20—P33 确认的 A 阶段范围、部署交付、正常/失败、网络/进程恢复及 2000 个标准变量参考规模。实现状态核对基线为 master@e486e45，续议时主线已到 b1fcd1a；本次没有重跑产品验收。

**核心模型已明确；首版 A 的交付与验收标准已定稿，进入实施规划。** 本文区分已确认的定义、当前主线记录的实现状态和后续阶段未决事项，不表示新 Flow、Agent Gateway 或 A 的交付验收已经完成；实施计划在专用工作树维护。

## 1. 产品定位与长期价值

MyFlowHub 是通用的节点协作平台：让技术用户或借助 AI 的用户，把不同能力接入为节点资源，在统一的发现、路由和权限机制下使用它们，再通过 Flow 组织成可持续运行、可追踪的自动化。

已确认的核心完成标准是：

> 技术用户或借助 AI 的用户，能接入一种新的能力，无须修改平台核心，就能从其他节点发现它、在授权下使用它，并与已有能力协作完成真实任务。

以下价值表述是对已确认需求的归纳：

- **能力可接入、可复用**：采集、设备控制、邮件、文件和剪贴板等通过同一资源模型协作；这些应用不限定平台用途。
- **标准资源可通用理解**：消费者理解平台契约即可使用标准资源，不必为每个提供者增加专用逻辑。
- **能力可组织**：人可以直接操作，Flow 可以自动运行，后续 Agent 可以通过受控入口访问。
- **行为可解释**：拒绝、不可用、事件缺口和执行失败有明确状态；用户能够判断发生了什么。
- **部署可选择**：物理设备、产品包与网络节点各有边界；功能可以组合，具体产品也可以保持独立交付。

来源：[本轮讨论 P01/P02/P04](../intake/2026-09-06_product-definition-grill.md)、[通用节点协作意图](flow-redesign.md)、[可扩展资源平台](extensible-resource-platform.md)、[统一变量原始请求](../intake/2026-09-06_unified-variable-contract.md)。

## 2. 用户与推进顺序

| 用户或能力 | 已确认定位 | 阶段约束 |
| --- | --- | --- |
| 技术型使用者 | 当前主要用户，可开发节点能力、配置网络及编写自动化 | 当前产品定义需要覆盖其完整使用路径 |
| 借助 AI 的使用者 | 当前目标用户，借助 AI 理解、编写或配置产品 | 不以 Agent Gateway 已存在为前提；具体辅助方式未定 |
| Agent 直接访问网络 | 完整产品需要具备的能力，通过 Agent Gateway 提供 | 其他部分充分完善后再实施，不能仅以接口趋稳代替这个前置条件 |
| 普通使用者 | 后续用户群 | 先完成产品，再做面向普通用户的指引和操作简化 |

普通用户支持后置不撤销现有 Desktop 的可访问性、错误解释、身份保护和必要技术说明要求。Android、嵌入式与实时媒体各有延期边界；它们是否属于 Agent 接入前必须完成的“其他部分”，尚未决定。

## 3. 网络与资源模型

### 3.1 节点、网络、资源

- 网络领域对象只有节点、网络和资源。节点是逻辑参与者，不等同于物理设备；一台设备可以运行多个节点。
- 只有节点提供资源，每个资源有明确的单一 owner，以 owner NodeID 与本地资源名称寻址。
- 权威节点树统一表达运行期拓扑、路由和相关 authority；非根节点在一个 authority 域内只有一个当前有效父节点。Transport 只提供承载，不产生另一套资源或权限模型。
- 产品名、进程、安装包、设备和插件都不构成网络特权。插件可以是节点内部实现方式。
- 一个节点可以实现部分或全部功能；不设置“一节点一功能”的通用限制。共享 NodeHost/SDK 也不意味着不同产品共享身份或状态。

来源：[节点拓扑发现](topology-discovery.md)、[统一节点运行时](unified-node-runtime.md)、[讨论 P07/P09](../intake/2026-09-06_product-definition-grill.md)。

### 3.2 资源类型与操作

资源类型定义对象的语义，capability 表达该对象允许怎样被操作。对已有资源的读取、订阅、写入等行为应归属于该资源；Command 用于节点额外提供、具有独立执行边界的能力。Flow 可以组织所有适用资源，不限于 Command。

| 类型 | 产品语义 | 需要保留的边界 |
| --- | --- | --- |
| Variable | 当前值、值定义、修订、质量状态及读取/写入/订阅 | 平台统一格式；只读/可写与最终授权分别表达 |
| Stream | owner 发出的事件序列 | 有界传递，明确事件缺口，不自动承诺持久回放 |
| Topic | 节点拥有的多发布者、多订阅者事件资源 | 发布与订阅分别授权；既有默认无 retention/replay，只保证单发布者顺序 |
| Command | 节点额外提供的执行能力，如发送邮件 | 输入、输出、期限和业务校验明确；不能把所有资源操作拆成独立命令 |
| File | 节点提供的受控文件传输能力 | 大数据通过有界 session/data lane；不是任意远程文件系统代理 |
| Collection | 管理可枚举、可定位的内部成员 | 成员默认是集合内身份，不自动成为全局资源；集合也不等于物理目录 |
| Flow | 动态部署、可触发的自动化程序资源 | 与 Command 分为不同类型；运行记录是内部记录，见第 5 节 |
| 自定义类型与 Media | 允许新增资源语义，Media 可使用描述与会话契约 | 仍须有节点 owner；生产级实时媒体未由此承诺完成 |

未知类型仍可被发现和查看描述；具体操作必须基于可理解的 capability/schema 和实际授权，不能猜测执行。资源名称中的路径分组只是展示组织，不创造新 authority tree。以上表格不是封闭类型枚举。

来源：[资源平台需求](extensible-resource-platform.md)、[Collection 与操作归属](../specs/resource-collections-and-actions.md)、[讨论 P09/P10/P15](../intake/2026-09-06_product-definition-grill.md)。

### 3.3 通用 Variable

Variable 不仅有统一操作接口，还应有统一的值、定义、状态和修订契约。Metrics 负责采集与业务适配，Desktop 按平台契约消费，不需要认识 Metrics 私有 payload、资源路径或预装其专用 schema。

- 提供者按平台语法声明实例的类型、范围、步长、枚举、单位和结构，业务校验可进一步收紧。
- 布尔、数字、文本、对象和数组保留真实类型；false、0、空字符串、null 和无可用值可以区分。
- 获授权消费者通过标准读取或订阅初始快照取得值定义与状态；只获 read 权限也能取得条件写入需要的修订信息。
- 写入在同一变量资源上表达，只修改值；owner 执行业务动作并返回真实结果，不伪造设备已执行成功。
- 陈旧或不可用必须显式表达，可保留最近真实值；不能用零值假装采集成功。
- Desktop 持续更新与未提交草稿分开管理；冲突、资源实例替换、断连和撤权都有明确处理。
- 定义是有界数据，不是远程代码或可执行 renderer。

这些是[统一变量需求](unified-variable-resource.md)与其[用户原始请求](../intake/2026-09-06_unified-variable-contract.md)中已有的产品结论。R2 已于 2026-10-09 在 6e6d5de 合入主线并归档，相关工作树已清理；验收范围和限制见[变更记录](../change/2026-10-09_unified-variable-contract.md)。

## 4. 准入、权限与信任边界

入网与使用资源是两件事。首次准入可以使用 Permit，或经过 Pending 审批；逻辑 Admission Authority 分配身份并下发 Grant。获得身份不会自动得到业务权限，也不会自动成为管理员。

网络授权针对明确 Subject Node、目标 Resource 和 capability。Policy Definition 表达可复用规则，Binding 绑定精确主体与 owner/subtree/authority-domain 作用域；未匹配时默认拒绝。产品名、同机部署和 UI 按钮可见性都不授予权限。当前父节点的显式控制权仍遵守权威树及控制阶段规则，owner 继续做输入和业务校验。

拓扑查询、catalog 读取和资源操作分别授权。Desktop 默认按需加载一层，搜索只覆盖已加载节点；看不到某段树不能直接推断资源不可用，读取失败也不能自动扩大全网查询范围。

| 边界 | 采用的约束 | 与其他边界的关系 |
| --- | --- | --- |
| 普通节点 | 身份、权威拓扑、策略与资源业务校验 | 所有产品共同遵守 |
| Flow 执行 | 使用承载节点的权限，不再设置逐 Flow 的资源/操作 scope | 部署到高权限节点意味着接受该权限执行的代价；契约校验与有界运行仍存在 |
| 外部 Agent 客户端 | Gateway 节点权限 ∩ Client Access Token scope ∩ API/schema/配额校验 | 外部客户端的访问边界，保留独立过期、撤销、限额和审计；不推导出逐 Flow 限权 |

Gateway 的 Client Access Token 与节点入网 Permit 不是同一种凭证。首期网络主体为 Gateway NodeID，外部 client/token 标记由 Gateway 管理；不伪装成其他节点。

## 5. Flow：已确认的产品定义

本节是本轮 Flow 产品结论的集中表述；逐项原话见[讨论 P04—P19](../intake/2026-09-06_product-definition-grill.md)。具体 API、wire、schema 与引擎仍由后续设计负责。

### 5.1 定义、部署与组织

- Flow 是由节点提供的独立资源类型，支持动态部署；Command 承载节点相对固定的额外能力。调用方式可以类似，不合并类型，也不把 Command 解释为永久不可变。
- 主要定义形式是可阅读、可版本管理的文本程序，优先使用成熟语言，优先采用节点进程内嵌引擎。
- Flow 运行能力可集成到普通节点，也可作为独立节点产品提供；独立部署是可选形态。
- Flow 可绑定变量变化、事件发布等触发条件；具体表达、组合方式和初始快照是否算触发尚未确定。
- Flow 的外部操作只能通过节点资源进行。外部服务先由节点接入，脚本中不能存在游离于网络资源体系之外的 HTTP、文件或系统指令入口。计算与控制逻辑仍可在程序内部完成。
- 按承载节点身份和权限操作资源，不新增逐 Flow 的授权层。

### 5.2 Flow 与 Run

Flow 保存程序、触发配置和已声明的持久状态。每次满足触发条件后形成可单独追踪的 Run，记录来源、输入、执行状态和结果；Run 是 Flow 内部记录，不新增网络基本对象。

同一个 Flow 默认串行执行，后续 Run 进入有上限的队列；队列满时明确记录拒绝原因。队列数值、持久化、取消与其他可选调度尚未决定。该规则不等同于把不同 Flow 全部串行化。

### 5.3 状态、重启和版本更新

- 作者显式声明需要持久化的状态，平台负责保存与恢复；普通局部变量不自动持久化。
- 重启默认从最近保存状态恢复；无法确认可安全继续时暂停并说明原因。不承诺任意指令位置恢复、零状态丢失或外部操作恰好执行一次。
- 程序与触发配置一起版本化。Run 固定使用创建时的版本；运行中和排队中的旧 Run 沿用旧版，新触发使用新版。
- 更新默认保留兼容状态；不兼容时暂停新版执行，由作者提供迁移方法或明确选择重置。
- 状态转换在旧版 Run 处理完、新版 Run 开始前进行。平台不会自动猜测业务语义兼容性。

恢复的精确粒度、保存时机、事件缺口、重试与副作用不确定性仍须定义。既有订阅重连机制不能直接充当持久事件回放或 Flow 恢复保证。

### 5.4 当前状态

旧 Flow 执行器和专属契约已经退役，新定义尚未实施。历史 `flow/definitions`、`flow/runs` Collections、图节点/边 schema 及旧授权传递方式不是新模型的合同。通用 Collection/capability 能力继续保留；管理 Flow 或 Run 是否使用集合操作尚未选定，不能借此抹去 Flow 独立资源类型的决定。

旧 `flow.json` 不读取、不执行、不自动迁移或删除；复用旧资源名不能自动继承旧授权。见[退役边界](flow-redesign.md)。

## 6. 产品组合与用户入口

下表区分产品职责和文档记录的状态。状态依据本次读取的仓库材料，未重新运行整套产品验收。

| 产品或能力 | 角色与关键边界 | 材料所示状态 |
| --- | --- | --- |
| Hub | 权威树根或中继宿主，承载身份、准入、路由、策略及管理资源；产品名本身不产生特权 | 现有产品；不是所有业务功能必须驻留的全局容器 |
| Desktop | 面向人的通用 Node/Resource 工作台，管理 Profile、浏览、预览、操作和可保存 View | 现有独立节点，默认 Parent-only；通用变量交互、节点刷新和紧凑卡片布局已提交至主线，相关文档另有未提交修改 |
| MetricsNode | 独立指标采集与受控设备执行产品，向网络提供标准变量等资源 | Windows 产品存在；标准变量改造已合入并归档，独立安装与升级等发布契约尚待验证 |
| ClipboardNode | 明确配置 peer 之间的文本剪贴板同步，有界历史、去重及正文保护 | Windows 产品存在；Web 是配置/UI 预览，不是浏览器节点 |
| File / filesystem | 文件传输用受控 session；目录/成员浏览用 Collection | 已有能力；任意文件系统代理、写删扩展和实时媒体不自动纳入 |
| Flow 运行能力 | 动态自动化资源与执行管理，可独立也可集成 | 核心产品定义已确认；旧实现退役，新实现待设计 |
| Agent Gateway | 独立、可无界面部署的普通节点 Web 服务，面向多个外部客户端 | 已有产品定义，实施后置；HTTP/MCP、token 格式和部署细节未定 |
| Android / 嵌入式 | 长期让移动与受限硬件上的能力进入同一网络 | 旧实现和构建门禁已移除，重新设计延期，未承诺重启时间 |

### 6.1 通用功能组合与独立产品交付

“一个节点可以组合多种功能”是通用模型；Desktop 与 Metrics 保持两个节点、两个进程、独立状态和安装包，是已有的具体产品要求。两者不互相否定：可以共享 Core、SDK 和无状态基础代码，不能因此合并身份、权限或让其中一个成为另一个的必装依赖。

本轮并未撤销该独立交付要求，也未撤销 Gateway 可脱离 Desktop 独立部署的要求。若未来要改变这些具体包装，应单独修改对应产品定义。已有两个二进制不能证明独立安装、升级、回滚、卸载已经全部验收。

### 6.2 Desktop 的补充要求

- Profile 隔离身份、连接和 Views；单实例当前只激活一个 Profile，切换释放旧连接、订阅和会话。
- Node tree 与资源路径分组分开呈现，按需发现；显示名帮助辨认节点，不替代 NodeID 或成为权限键。
- 提供者定义数据语义与有效域；Desktop 选择兼容的本地 renderer，用户可保存展示偏好。标准 Variable 的定义语法必须属于平台。
- View 保存资源引用、renderer、布局与允许的非秘密展示设置，不复制资源值、权限或凭据；它也不是 Flow 程序或执行状态。
- 资源离线、撤权、schema 不兼容等状态应可解释，不能静默丢掉 View 布局或未提交草稿。
- 统一品牌和低噪声、可访问的交互要求继续保留；品牌图标不承担资源类型图标的职责。

## 7. 冲突与补充核对

| 事项 | 资料差异 | 统一后的处理 |
| --- | --- | --- |
| 资源类型是否固定 | 早期 README/运行时描述突出 Variable、Stream、Command；后续资源平台允许 Topic、File、Collection、自定义类型 | 采用可扩展类型模型；早期列举不能视为封闭枚举 |
| 节点是否等于设备 | 早期资料沿用设备措辞，后续产品与拓扑定义明确逻辑节点 | 一个设备可有多个节点；设备、进程和插件不增加网络对象 |
| 平台变量还是产品 payload | 历史 Metrics/renderer 资料使用专用包装，统一变量 R2 明确消费者无需认识提供者 | 主线已切换为平台通用 Variable；旧包装与被替代的 /set 不再是当前合同，见 R2 归档 |
| Metrics 控制方式 | 历史定义使用 Variable + 独立 /set Command；R2 要求同资源 write | 主线已实现标准 write 并移除被替代的 /set；其他独立业务 Command 保留 |
| Provider schema 的含义 | 旧阶段仅支持内置 schema，通用变量要求通过网络理解新实例 | 平台定义变量格式，provider 声明实例语义，Desktop 选择 renderer；非 Variable 的通用远程 schema 服务仍另行设计 |
| Flow 模型、执行身份与状态 | 旧规格是集合成员/图模型并保留原始 initiator；本轮明确独立 Flow 类型、文本程序、宿主节点权限和显式持久状态 | 旧规格已标记历史；以第 5 节为新产品定义，不能恢复旧执行器或旧授权规则 |
| Flow 是否尚未决定任何方向 | 退役待办把宿主、语言路线、状态、并发都列为未知 | 其中已由 P04—P19 确认的事项转为定义，具体引擎和未决语义仍保留待办 |

## 8. 已拒绝、已延期与尚未决定

### 已拒绝或由新结论取代

- 强制一节点只承载一种功能、强制 Flow 必须作为专用节点。
- 为每条 Flow 再设独立资源/操作授权 scope。
- 将 Flow 归并为 Command，或让 Flow 只能操作 Command。
- Flow 直接执行网络资源体系之外的外部指令。
- 以补 Metrics 专用 schema、猜资源路径或维持产品变量包装作为通用 Variable 的最终方案。
- 将旧 Flow 图模型、Collections 或原发起者授权链直接当作新 Flow 合同。

### 已延期

Agent 直接接入在其他部分充分完善之后；普通用户支持在产品完成之后。Android、嵌入式重设计、生产级实时媒体和非 Variable 的通用远程 schema 服务保留既有延期边界。延期事项是否进入某个版本，需要明确范围，不能把“延期”理解为“已经完成”。

### 已确认的首版阶段（P20）

用户选择先做 A，“先把基础能力打扎实”。首个交付阶段为 Windows 上 Hub、Desktop、Metrics 的接入、发现、授权、读取、订阅与手动控制；新 Flow 后续推进。Clipboard/File 现有能力保留回归，专门增强及完整交付验收不自动纳入本阶段。Agent Gateway、Android、嵌入式及普通用户操作简化保持后置。

这是交付顺序的选择，保留 P01—P19 以及完整产品的自动协作目标；不将 B/C 视为永久拒绝，也不把 A 完成自动等同于 Agent Gateway 的前置门槛已满足。A 的交付、生命周期、真实环境和失败恢复标准已由 P21—P33 收束，见[当前续议与 P20](../intake/2026-09-06_product-definition-grill.md#p20--先完成-a把基础能力打扎实)。

### 已确认的 A 主验收场景（P21）

技术用户从干净环境开始，在真实跨设备网络中完成产品部署、节点准入与明确授权；Desktop 发现 Metrics、持续查看真实指标，手动修改一个获授权的设备状态并回读实际结果；撤权后明确拒绝操作，断网和重启后按预期恢复，身份、配置和视图保留。

本场景已确认。P22 明确首次部署、准入和授权管理可以用命令行，日常查看与控制通过界面完成。P23 确认两台 Windows 设备在同一局域网通过 TCP 连接：A 运行 Hub/Desktop，B 运行 Metrics，两个客户端节点独立接入 Hub。P24 确认独立可运行包加完整部署说明作为交付基线，安装向导与自动更新后置。P25 确认先以 Windows 11 x64 正式验收，Windows 10 和 ARM64 后续评估。P26 确认设备 B 系统主音量/静音控制组，P27 确认其正常取值、容差及响应时间。P28—P33 已进一步确认异常恢复、并发、2000 个变量每秒更新、稳定性及独立生命周期。实际系统构建号与工具在执行前核实。详细边界与定稿标准集中维护于[A 阶段验收标准](phase-a-acceptance.md)，不重复把已确认事项列为待选择。
