# Build, generation, packaging, and CI contract

## Canonical entry

All local and CI build logic enters through `scripts/mfh.ps1`. The script always sets `GOWORK=off`, resolves paths from its own repository root, fails on missing mandatory tools, and only skips environment-specific work when the caller explicitly passes `-AllowUnavailable`.

```powershell
./scripts/mfh.ps1 -Action list
./scripts/mfh.ps1 -Action test -Target core
./scripts/mfh.ps1 -Action build -Target desktop
./scripts/mfh.ps1 -Action generate -Target generated
./scripts/mfh.ps1 -Action check -Target all -AllowUnavailable
./scripts/mfh.ps1 -Action manifest
```

`all` has a fixed order: core, Hub, Desktop, MetricsNode, ClipboardNode. A focused target does not install or probe unrelated product tools.

## Toolchain truth

`build/toolchain.json` pins Go, Node.js, Wails and Flutter. Go modules, npm lockfiles and the Flutter lockfile are committed inputs. Executables, Flutter build output and node_modules are ignored outputs.

Flutter is installed by CI at the pinned version. A local SDK outside PATH can be selected using the absolute `MFH_FLUTTER_HOME` path. The script validates bin/flutter (or bin/flutter.bat) and applies it only for the invoked process.

Android/embedded source, targets and CI jobs are retired. JDK, Android SDK, gomobile/x/mobile, Gradle, C SDK tooling and ESP-IDF are no longer project build inputs; old mobile environment overrides are removed. Local SDK installations are not deleted. See [redesign backlog](../requirements/mobile-embedded-redesign.md).

## Generated source

- `sdk/bindings/generated/contracts.json` is generated by `go generate ./sdk/bindings` and independently regenerated in its Go test. Its repository line ending is fixed to LF so byte-level freshness checks behave identically on Windows and CI.
- `methods` and `desktop_methods` describe the actual portable and Desktop attached binding Clients. Product UI methods such as Wails file selection are outside this manifest. Tests compare both method lists with the exported Client APIs.
- Desktop and Metrics Wails bindings are generated from canonical Go application types. Their tracked `index.html`, `dist/`, and `wailsjs/` trees use repository-forced LF so Windows generation and frontend builds do not create line-ending-only diffs.
- `check/generated` regenerates source and rejects a tracked diff in CI.

## Product gates

| Target | Tests | Build outputs |
| --- | --- | --- |
| core / Hub | full Go tests, vet, architecture and migration guards | root `out/bin` Go CLIs |
| Desktop | Go host/binding, Vitest, TypeScript/Vite | Wails Windows binary |
| MetricsNode | Go core/platform, Vitest, TCP process | Wails Windows binary |
| ClipboardNode | Go core/bridge, Flutter analyze/widget | Windows bundle + bridge, Web preview bundle |

## CI rules

The single `canonical-ci` workflow has no path filter: every protocol/runtime/shared SDK change reaches every product job. Jobs have read-only repository permissions, pin the project tool versions, and upload build artifacts without publishing a release. Bluetooth hardware tests, signing, stores, and remote releases remain separate explicitly authorized gates.

## Artifact manifest

After selected builds, `-Action manifest` writes `out/artifact-manifest.json` with repository-relative paths, byte lengths, and SHA-256 values. The manifest only describes files that exist; absence is an error rather than an empty successful package.
