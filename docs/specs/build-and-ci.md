# Build, generation, packaging, and CI contract

## Canonical entry

All local and CI build logic enters through `scripts/mfh.ps1`. The script always sets `GOWORK=off`, resolves paths from its own repository root, fails on missing mandatory tools, and only skips environment-specific work when the caller explicitly passes `-AllowUnavailable`.

```powershell
./scripts/mfh.ps1 -Action list
./scripts/mfh.ps1 -Action test -Target core
./scripts/mfh.ps1 -Action build -Target desktop
./scripts/mfh.ps1 -Action generate -Target generated
./scripts/mfh.ps1 -Action check -Target all -AllowUnavailable
./scripts/mfh.ps1 -Action manifest
```

`all` has a fixed order: core, Hub, Desktop, Android, MetricsNode, ClipboardNode, Embedded. A focused target does not install or probe unrelated product tools.

## Toolchain truth

`build/toolchain.json` is the human- and machine-readable tool version inventory. Go module versions, npm lockfiles, Gradle wrappers, Flutter lockfile, the ESP-IDF version, and the ESP32 libsodium component are committed inputs. Generated AARs, APKs, executables, CMake state, Gradle state, `node_modules`, and ESP-IDF managed components are ignored outputs.

Android builds use JDK 17 in CI. A developer whose system `java` points at a newer incompatible runtime can set `MFH_JAVA_HOME` to a JDK 17/21 installation; the root script validates and applies it only for the invoked process.

Flutter is installed by CI at the version pinned in `build/toolchain.json`. A local SDK that is not already on `PATH` can be selected with the absolute `MFH_FLUTTER_HOME` path; the root script validates `bin/flutter` (or `bin/flutter.bat`) and applies it only for the invoked process.

The Android SDK comes from `ANDROID_HOME` or `ANDROID_SDK_ROOT`. On Windows only, an unset environment is resolved from the standard `%LOCALAPPDATA%\Android\Sdk` location when it exists; the build never commits or fabricates a machine-specific `local.properties` file.

Some sandboxed Windows hosts virtualize `%TEMP%` into a path that exceeds the JDK AF_UNIX socket limit, causing Gradle to fail before project configuration with `Unable to establish loopback connection`. `MFH_SHORT_TEMP` may point to an explicitly chosen short absolute temporary directory for that host; it is not a project cache or a CI requirement.

## Generated source

- `sdk/bindings/generated/contracts.json` is generated by `go generate ./sdk/bindings` and independently regenerated in its Go test. Its repository line ending is fixed to LF so byte-level freshness checks behave identically on Windows and CI.
- Desktop and Metrics Wails bindings are generated from canonical Go application types. Their tracked `index.html`, `dist/`, and `wailsjs/` trees use repository-forced LF so Windows generation and frontend builds do not create line-ending-only diffs.
- Android AARs are generated from the single Go module with the pinned `x/mobile` tools; Gradle builds require the matching AAR and must not compile a local stub.
- `check/generated` regenerates source and rejects a tracked diff in CI.

## Product gates

| Target | Tests | Build outputs |
| --- | --- | --- |
| core / Hub | full Go tests, vet, architecture and migration guards | root `out/bin` Go CLIs |
| Desktop | Go host/binding, Vitest, TypeScript/Vite | Wails Windows binary |
| Android | Go binding, JVM unit, Android lint | dual-ABI gomobile AAR and debug APK |
| MetricsNode | Go core/platform, Vitest, JVM unit/lint | Wails binary, dual-ABI AAR, debug APK |
| ClipboardNode | Go core/bridge, Flutter analyze/widget | Windows bundle + bridge, Web bundle, dual-ABI APK |
| Embedded | warning-as-error C/CTest, MicroPython host tests, Go fixture parity | C library and ESP32-S3 firmware |

## CI rules

The single `canonical-ci` workflow has no path filter: every protocol/runtime/shared SDK change reaches every product job. Jobs have read-only repository permissions, pin the project tool versions, and upload build artifacts without publishing a release. ESP32 uses the ESP-IDF 6.0.2 container. Hardware flash, Bluetooth, signing, stores, and remote releases remain separate explicitly authorized gates.

## Artifact manifest

After selected builds, `-Action manifest` writes `out/artifact-manifest.json` with repository-relative paths, byte lengths, and SHA-256 values. The manifest only describes files that exist; absence is an error rather than an empty successful package.
